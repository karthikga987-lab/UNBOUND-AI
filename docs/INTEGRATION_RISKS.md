## High and medium risks

| Risk | Impact | Current mitigation / required test |
|---|---|---|
| Task/event/approval state is process memory | Restart loses tasks; multiple worker processes do not share state | Keep one process for MVP rehearsal; disclose limitation. Do not claim durable recovery. |
| Verifier or registry changes during execution | Could create a safety/configuration race | Verifier update waits until active executor runs finish and applies to later runs. Register tools during startup; concurrent registry mutation during planning/execution is unsupported. |
| Browser replay hides stored workflow actions behind an ID | Action sensitivity cannot be fully classified from caller arguments | Replay requires approval under current policy; Member 2 must preserve per-action verification and avoid hidden consequential actions. |
| External cancellation semantics | In-flight remote action may already have taken effect | Cancellation prevents later steps; it cannot guarantee rollback of an already-started action. Test both before-claim and in-flight cases and communicate outcome honestly. |
| Evidence may be mistaken for proof of success | UI/report could overstate unverified claims | Evidence is retained with provenance on verification failure; display verification status separately and never render retained evidence as success by itself. |
| Synthetic fixture can be confused with research | Demo could present invented values as real findings | Mark all fixture docs, site data, IDs, citations and output SYNTHETIC; never mix fixture facts with real-world claims. |
| Shared test environment/provider settings drift | Failures or accidental external requests during integration | Use fake providers in tests, controlled local browser fixtures, explicit provider configuration and no live write targets. |
| Personal-memory retrieval is lexical and local-only | Relevant paraphrases may be missed; no user identity boundary exists | Member 3 | Keep retrieval bounded and opt-out enabled; add semantic retrieval only as a separately reviewed future phase; do not expose API beyond localhost without auth. |
| Assistant intent is LLM-classified with schema validation | A schema-valid label can still misunderstand intent; the prototype therefore requires distinct classify, consent, execute, and approval actions | Member 1 + 3 | Keep conversation response-only. Treat planning as non-executing; preserve explicit task execution and backend approval/verifier gates in the React integration. |
| Intent labels are model-generated even though schema-validated | A wrong but schema-valid category can lead to an irrelevant clarification or an unnecessary planned task | Member 3 | Require current-turn authorization for action execution; never execute during classification/planning; retain explicit execute, approval, verifier, and cancellation boundaries. |
| API authentication and multi-user authorization are absent | Any local process/user that can connect to loopback can read/delete sessions and manage global personal memories or task routes | Member 3 before any remote deployment | Runtime rejects non-loopback peers, invalid local Hosts, and untrusted mutation Origins, but these controls do not authenticate local clients. Keep strictly local; implement auth and ownership before network access. |
| There is no request rate limiter | A local client can repeatedly invoke model/database work within the 1 MiB request cap | Member 3 / deployment owner | Keep loopback-only; add rate/concurrency controls before exposing an authenticated service beyond one user's local process. |
| SQLite is not encrypted at rest | Device/account compromise or database-file access can expose conversations and approved memories | User / deployment owner | Keep the file in the user-private application data directory; use OS disk/account protection; avoid secrets in prompts. |
| Prompt injection remains probabilistic | Malicious messages, memory text, websites, documents, or MCP content may influence model output despite system rules | All members | Treat external content as data and enforce through registered tools, parameter validators, approvals, and independent verifiers. Never rely on prompt text alone. |
| Failed or interrupted external side effects can have unknown outcomes | Retrying can duplicate a purchase, message, submission, or other action | Member 3 + adapter owner | Recovery blocks ambiguous failed/running steps in `NEEDS_ATTENTION`; reconcile the target system manually before creating a new task. No durable task journal exists. |
| Tool/provider error details can contain sensitive data | Raw exceptions, paths or adapter output could appear in logs or task responses | Member 3 + adapter owners | API logs only exception class for unexpected failures; tool errors and input diagnostics are content-minimized. Continue auditing adapter-owned logs. |

## Current implemented versus pending

- **Implemented in this checkout:** shared Pydantic 2 contracts; intent and planning; FastAPI health/task/conversation/personal-memory/execute/cancel/events/approval routes; shared injectable TaskRuntime; ToolRegistry schema/input validation; task state and events; approval gates; per-tool/shared verifier selection; verifier update synchronization against active runs; evidence ownership/retention; cancellation and recovery tests; SQLite conversation history and controlled, approval-gated personal memory.
- **Implemented in this checkout:** isolated browser voice prototype with push-to-talk, text fallback, session restoration, speech output controls, and explicit task handoff through existing assistant/task APIs. It has browserless Node tests but still requires a manual Edge microphone/synthesis check.
- **Implemented in this checkout:** PDF/DOCX/TXT ingestion through bounded multipart upload, isolated SQLite document metadata/chunk storage, document listing/search, context retrieval and relationship analysis, evidence provenance, three read-only registered document/context tools with tool-specific verifiers, and a standalone read-only MCP server. Local filesystem import as a task tool is disabled unless an import root is configured and then requires approval.
- **Implemented but blocked in this checkout:** browser modules, encrypted replay-state composition, TaskManager-bound continuation authorization, six ToolRegistry registrations, a loopback connection-pinned HTTP/HTTPS proxy, and a context-wide non-web-scheme gate. The runtime gate remains hard-disabled because Playwright is unavailable for live proxy-bypass tests and the application has no OS-level restriction preventing a browser process from opening non-proxy sockets. **Pending:** reviewed connection-time enforcement, browser HTTP/event routes and Live View, spreadsheet extraction, cross-document comparison/report generation, and external MCP client connections. React chat/task workspace is present; workflow/document/integration data panels are explicitly mocked, and personal-memory management remains API-only without a dedicated UI.
- **Known runtime limit:** in-memory task state does not survive restart or coordinate across multiple worker processes. Use one API worker for the MVP unless runtime state is redesigned.
- **Security controls in this checkout:** loopback peer check; allowlisted Host and mutating Origin; 1 MiB request body cap; CORS allowlist; content-minimized unexpected-error/tool diagnostics. There is no authentication, authorization, rate limiting, encryption-at-rest, or protection from a hostile local process. Do not expose through network interfaces, tunnels, or reverse proxies.
- **Recovery policy:** conversation/memory persist in SQLite; task/event/approval state does not. No restart replay occurs. Explicit recovery refuses to retry failed/interrupted steps with uncertain side effects.

## Go/no-go

Do not advertise the flagship as end-to-end ready until each critical blocker has a real implementation, is registered under its agreed name, has a nontrivial verifier, passes its component test, and passes the synthetic full-flow rehearsal with source-linked evidence and correct UI state. Unit tests using fake tools validate orchestration only; they do not close integration blockers.

## Reminder and wake-word limitations

- Reminders persist as a separate local SQLite domain, require confirmation, and never invoke task execution. The optional Windows user-session agent must be explicitly installed and running; conversational wording uses the shared cached agent status and avoids promising delivery when status is unknown.
- The default openWakeWord runtime and microphone adapter are implemented and imported in isolated Python 3.14.4 environments. The exact custom classifier has not been trained, installed, or tested against live microphone audio. The openWakeWord code is Apache-2.0, but the trainer's bundled feature-model Apache notice conflicts with the upstream README's blanket CC-BY-NC-SA notice for included pretrained models; commercial use remains unapproved pending license review. Do not use the ACAV100M-derived negative feature corpus. Browser SpeechRecognition after activation may still use an online recognition service.
- Stop Speaking now invalidates pending auto-playback as well as active/queued utterances. Node mocks exercise cancellation and stale callbacks; actual Edge audio cancellation remains a required manual check and is not claimed verified.
- The current live Ollama sample suite succeeded, but it did not reproduce the previously observed intermittent HTTP 503. A single retry of transient connection errors/502/503/504 improves recovery but does not prove provider availability or eliminate later failures.
- Windows notification submission is not confirmation of visual display. Toast settings, Focus Assist, session state, and Windows app identity setup can prevent a visible alert; validate actual toast behavior on the target Windows device before relying on it.
