# UNBOUND AI API Contract

The health, conversation, assistant-intent, task, memory, approval, document, and context endpoints listed below are implemented by the existing application in `backend/app/main.py`. Browser workflow and integrations endpoints remain future interfaces. JSON task models use the shared Pydantic 2 contracts; document API models are local to that API module.

Errors use `{"detail":{"code":"stable_error_code","message":"human-readable explanation"}}`. Responses must not expose credentials or internal stack traces.

### Local deployment security boundary

The API middleware accepts loopback network peers only, allows local Host values, rejects non-allowlisted browser Origins on state-changing methods, and rejects request bodies larger than 1 MiB (including chunked bodies), except document upload which allows up to 21 MiB of multipart body for a 20 MiB file limit. CORS is limited to the local voice prototype/API origins. These are local-prototype exposure controls, not authentication: any local process that can connect to loopback can still access all sessions, memories, and task APIs. Do not bind to a network interface, expose through a tunnel, or rely on CORS as access control. Authentication and per-user authorization are required before remote or multi-user deployment. No rate limiter is currently implemented.

## Optional local wake word

Wake detection is disabled until the user calls the start endpoint or presses the voice UI control. The backend loads the configured openWakeWord ONNX classifier and local feature models and owns the microphone; the browser polls for an activation event after starting. `UNBOUND_WAKE_MODEL`, `UNBOUND_WAKE_FEATURE_DIR`, and `UNBOUND_WAKE_THRESHOLD` are local configuration and are never returned by these endpoints. No task is created or executed by wake detection. The exact custom classifier is not yet available in this checkout.

| Method / path | Purpose | Request | Response | Errors / safety |
|---|---|---|---|---|
| `GET /api/wake-word/status` | Read detector state without opening the microphone. | None. | `status`, `enabled`, `local_audio`, `phrase`, safe `detail`, `event_id`. | `200`; does not initialize the optional engine. |
| `POST /api/wake-word/validate` | Initialize/release the model to verify classifier, feature files, and runtime without creating an audio recorder. | None. | `{"valid":true,"phrase":"hey unbound","microphone_opened":false}`. | `503` if dependency, model, feature assets, or native initialization is unavailable. |
| `POST /api/wake-word/start` | Explicitly start local detection and microphone capture. | None. | Detector status. | `503` when disabled prerequisites, permissions, or audio devices prevent start. No startup task runs it automatically. |
| `POST /api/wake-word/stop` | Stop detector and release audio resources. | None. | Detector status. | Idempotent; app shutdown also stops the detector. |
| `GET /api/wake-word/events?after_event_id={integer}` | Poll for a new local activation after the audio resource has been released and renew the UI listener lease. | Nonnegative cursor. | `{"event": event|null, "status": WakeWordStatus}`. | No audio or transcript is returned. Monitoring stops and releases the microphone after 5 seconds without UI polling. |

This component is process-local and should be run in one backend worker. Runtime dependencies install only into `.venv-wake`; CPU training dependencies install separately into `.venv-wake-train`. The main Python environment and standard backend requirements remain unchanged.

## Tasks

| Method / path | Purpose | Request | Response | Errors / approval |
|---|---|---|---|---|
| `POST /api/tasks` | Classify a request and create a plan only when it is actionable. | `TaskCreateRequest` (`user_request`, `auto_execute=false` by default). | `TaskResponse` for actionable requests. | `422 not_a_task_request` for conversation/information/drafting, directing clients to `/api/assistant/requests`; `422 task_clarification_required` for ambiguous requests; `422 invalid_plan`; `503` provider unavailable. No task is created on these errors. |
| `GET /api/tasks/{task_id}` | Retrieve task state, plan, approvals, evidence, artifacts, and result. | UUID path parameter | `TaskResponse` | `404` unknown task. No approval. |
| `POST /api/tasks/{task_id}/execute` | Start or continue eligible task steps. | No body. | `TaskResponse` | `404` unknown task; state outcomes, including awaiting approval and verification attention, are returned in `TaskResponse`. Mandatory approvals remain required. |
| `POST /api/tasks/{task_id}/cancel` | Request cancellation. | No body. | `TaskResponse` | `404` unknown task. Cancellation of terminal tasks is idempotent. No approval. |
| `GET /api/tasks/{task_id}/events` | Retrieve ordered execution events. | UUID path parameter | `list[ExecutionEvent]` | `404` unknown task. No approval. |
| `POST /api/tasks/{task_id}/approvals/{approval_id}` | Resolve one pending approval. | `{"decision":"APPROVED"}` or `{"decision":"REJECTED"}` | Updated `TaskResponse` | `404` unknown task or pending approval; `422` invalid decision. Approval does not start execution; an approved task returns to `created` and requires a separate explicit execute request. |

Task creation first uses the existing structured assistant intent classifier. Conversation, information, drafting, and clarification-required messages do not create tasks. Actionable requests then pass through the task intent extractor and structured planner. Missing LLM configuration or provider failure returns `503`; malformed or unsafe planner output returns `422` and is not stored as an empty task. Intent-stage and plan-stage clarification counts are recorded as separate execution events, while the task result retains the actual missing-information prompts. `auto_execute` defaults to false; when true, the existing executor is invoked only after planning succeeds and still enforces approval and verification. Missing information or an empty/invalid plan is never executed. If no verifier exists, the executor leaves the task needing attention without invoking a tool. A post-call tool exception, unsuccessful result, or failed/unavailable verification leaves the task in `needs_attention`; the external result is uncertain and generic execute does not retry it.

Each `TaskStep` includes `depends_on: list[str]`. Empty dependencies on later draft steps are normalized to depend on the immediately preceding step, preserving the sequential planner behavior; explicit dependencies may refer only to unique earlier steps. The executor stops a dependent action when a prerequisite did not complete with verification.

## Explicit assistant request routing

| Method / path | Purpose | Request | Response | Errors / safety |
|---|---|---|---|---|
| `POST /api/assistant/classify` | Classify one current chat turn so clients can choose between normal conversation and task preparation. It does not answer, persist, create a task, or execute tools. | `{"message": string, "session_id"?: UUID4}`. When supplied, bounded session history is context only. | Validated `AssistantIntent` with `category`, optional `clarification_question`, and `current_turn_authorizes_execution`. | `422` invalid/sensitive message; `404` unknown session; `503` provider unavailable or malformed classifier output; `500` context unavailable. Deterministic local-file and reminder routing reuses existing backend handlers. |
| `POST /api/assistant/requests` | Classify an explicitly submitted request; answer conversation/information/drafting requests, ask clarification, or create a task plan for action planning/execution intent. | `{"message": string, "session_id"?: UUID4}`. When supplied, the existing session provides bounded context. | `AssistantRequestResponse` (`intent`, `reply`, `task` nullable). A completed request is appended to the session as a user/assistant exchange. | `422` invalid/sensitive message; `404` unknown session; `503` provider unavailable or malformed classifier output; `422` unsafe plan; `500` conversation persistence failure. Classification and task creation never execute tools. |

The classifier returns one of `conversation`, `information`, `drafting`, `action_planning`, `action_execution`, or `clarification_required`. Its Pydantic output is validated. An action-execution classification without current-turn authorization is downgraded to clarification. History may resolve a referent but is never fresh authorization; personal memories are not sent to the classifier. Only registered tools are passed to the planner. If needed details are missing, the endpoint returns a focused clarification and does not create a task. For session-backed requests, the completed reply or plan message is persisted so the next turn can use it as context. Otherwise the response may contain a `TaskResponse` plan; it always sets `auto_execute=false`. The client must use the existing task execute endpoint explicitly. Consequential steps remain approval-gated.

An explicit current-turn request to open/read/analyse/summarize/review/inspect one absolute Windows path ending in `.pdf`, `.docx`, or `.txt` is handled deterministically as a one-step `document.read_local_file` task. The response names the exact requested path and states that it has not been opened. The client calls the task execute endpoint to create a pending approval, presents the approval request, submits `APPROVED` through the existing approval endpoint, then explicitly calls execute again. Approval is bound to the exact path and a file identity/size/mtime snapshot, expires after 10 minutes, and cannot be reused; if the file changes, execution fails and requires a new request. This feature is read-only and single-file, rejects network paths and links/reparse points, and defaults to 20 MiB. It stores the approved document in the existing `%LOCALAPPDATA%\UNBOUND\documents` store. Analysis is limited to retrieved extracted chunks and uses only a loopback Ollama provider; findings are accepted only when their quoted evidence is an exact substring of a cited chunk. The ordinary `/api/conversation` endpoint remains unable to create tasks or read files. This is not unrestricted filesystem access, a file browser, or a remote upload feature.

## Conversation

| Method / path | Purpose | Request | Response | Errors / safety |
|---|---|---|---|---|
| `POST /api/conversation` | Return a conversational response for voice or text input; explicit reminder commands are routed to the local reminder service. | `{"message": string, "history": [{"role":"user"|"assistant","content":string}], "timezone"?: IANA zone}`; history defaults to `[]`, max 12 turns, text max 4000 chars per message. | `{"reply": string}` | `422` empty/invalid input/time zone; `503` provider unavailable; `500` local reminder storage failure. This route does not create tasks, invoke task tools, or execute external actions. |

The stateless endpoint above remains available for compatibility. Conversation context is assembled by the assistant layer: it uses bounded recent history, relevant approved memories only when memory retrieval is enabled, and the current registered task-tool inventory. History, memory, and capability metadata are supplied as data separate from system instructions. The assistant is instructed to maintain a consistent UNBOUND identity, distinguish information/drafting/planning from action requests, ask a focused clarification when essential information is missing, and avoid claiming unavailable capabilities or unverified results. Memory retrieval remains keyword-based; the model may still misunderstand context or intent.

`POST /api/conversation` and persistent conversation session routes never call task tools or create/execute tasks. Explicit reminder commands are recognized before LLM response generation and use the same reminder service as `/api/reminders`; supported phrasing includes “remind me about…”, “create a reminder/remainder for…”, “I need to remember to…”, and “don’t let me forget…”. Missing dates are clarified; when a date is supplied without a time, the assistant asks whether to set a specific time or an all-day reminder. A proposal is saved as `proposed` and requires an explicit confirmation before activation. The stateful conversation request accepts an optional browser IANA `timezone`; otherwise `UNBOUND_TIMEZONE` (default `UTC`) is used. “Set it up on my laptop” means store the reminder locally in UNBOUND. A Windows toast is submitted only if the separate Windows notification agent has been explicitly installed and is running. A reminder is not a personal memory or task. Clients may opt into task intent routing through the separate `POST /api/assistant/requests` endpoint. Alternatively, a user/client may explicitly submit a task through `POST /api/tasks`; execution is a separate `POST /api/tasks/{task_id}/execute` request. Approval and verification rules continue to apply. A wish, hypothetical, prior transcript, or memory does not authorize an action. The isolated voice prototype has a separate user-triggered classify/plan action and requires a further explicit consent checkbox, execute action, and confirmation before calling the task execute route. Approval decisions also require an explicit user action and never trigger execution automatically.

Persistent local sessions use these additional endpoints:

| Method / path | Purpose | Request | Response | Errors / privacy |
|---|---|---|---|---|
| `POST /api/conversations` | Create an empty conversation session. | No body. | `ConversationSession` (`session_id`, timestamps, `message_count`). | `201`; `500` local storage unavailable. |
| `GET /api/conversations` | List local sessions, newest updated first. | None. | `list[ConversationSession]`. | `500` local storage unavailable. There is no authentication or per-user isolation in this single-user prototype. |
| `GET /api/conversations/{session_id}` | Retrieve one session and its ordered messages. | UUID4 path parameter. | `ConversationHistory` (`session_id`, timestamps, `messages`). | `404` unknown session; `422` invalid UUID4. |
| `GET /api/conversations/{session_id}/tasks` | Restore task references associated with this chat for the React task workspace. | UUID4 path parameter. | `ConversationTaskReferences` (`session_id`, `available_task_ids`, `unavailable_task_ids`). | `404` unknown session; `500` local storage unavailable. It returns IDs only; `TaskManager` remains the task source of truth. |
| `POST /api/conversations/{session_id}/messages` | Generate and persist a user/assistant exchange using prior stored context or handle an explicit reminder command. | `{"message": string, "request_id": UUID4, "timezone"?: IANA zone}`; `request_id` is generated if omitted and should be reused when retrying the same submission. | `ConversationExchange` (`session_id`, `reply`, `user_message`, `assistant_message`). | `404` unknown session; `409` request ID reused with different text; `422` invalid input/time zone; `503` provider unavailable; `500` persistence failure. A successful retry with the same request ID returns the persisted exchange. |
| `DELETE /api/conversations/{session_id}` | Delete a session and cascade-delete its messages. | UUID4 path parameter. | `204` no content. | `404` unknown session; `422` invalid UUID4. |

Persistent conversation messages and session-to-task references are stored locally in SQLite, separately from task state. The link table stores task IDs only; `TaskManager` remains authoritative for task records. `UNBOUND_CONVERSATION_DB` optionally selects the database file; otherwise Windows uses `%LOCALAPPDATA%\UNBOUND_AI\conversations.sqlite3`, and other platforms use `$XDG_DATA_HOME/unbound-ai/conversations.sqlite3` or `~/.local/share/unbound-ai/conversations.sqlite3`. The backend limits context to the most recent `CONVERSATION_MAX_TURNS` complete turns (default 12, maximum 100) and `CONVERSATION_MAX_CONTEXT_CHARS` characters (default 12000, range 4000–64000). Old complete turns are omitted; message text is not truncated. The stateless compatibility endpoint still accepts client-supplied untrusted history. Conversation routes never invoke orchestration or execute tasks. For a session-backed follow-up about a linked completed document task, only its independently verified findings and matching evidence excerpts are supplied as untrusted context, and only to a verified loopback Ollama provider. Multiple matching documents require clarification. If the backend restarted and the linked task is unavailable, UNBOUND says so and does not reopen the file. Task IDs/events/approvals/results remain in memory and are lost on restart; SQLite links do not make task state durable.

Session IDs are UUID4 references rather than authorization credentials. The API has no authenticated ownership boundary; session-specific routes prevent accidental cross-session query mixing, but a client able to reach this local API can list and read any session. Personal memories are intentionally global to the single local user and may be retrieved across sessions when enabled. SQLite is not encrypted at rest. Conversation messages, relevant approved memories, and context are sent to the configured provider; local Ollama stays on-device under the default local configuration, while cloud providers can transmit content outside the device.

The React ChatPanel first calls `/api/assistant/classify` for each submitted turn. `conversation`, `information`, and `drafting` turns use the persistent session/message endpoint; action and clarification turns use `/api/assistant/requests`, which prepares a task only when allowed by the existing backend classifier and planner. Task controls use the task response fields (`status`, `plan`, `pending_approvals`, `evidence`, `result`, `error`), task events, approval route, and explicit execute route. Chat does not call tools directly. A prepared plan is not execution; task execution requires the separate explicit Run plan action, and approval resolution does not resume execution. The standalone `experiments/voice-prototype/` continues to use the persistent conversation endpoint and its separate explicit plan handoff. See its README for local startup, browser permission, and speech privacy details.

The persistent message endpoint rejects common recognizable credential formats before provider use or storage, but this heuristic is not a secret scanner; do not enter passwords, API keys, or authentication secrets. Ordinary assistant replies are prompt-guided; intent routing is separately schema-validated but can still misclassify. Prompt-injection guidance is defense-in-depth, not a guarantee. External content and memories are supplied as data and cannot authorize an action; the separate task API, registered tools, approvals, and verifier boundaries remain mandatory.

## Controlled personal memory

Personal memory is stored in separate SQLite tables in the same local database as conversation history. Categories are `fact`, `preference`, `project`, `recurring_context`, `instruction`, and `other`. Only approved memories marked `user_confirmed=true` can be retrieved for a conversation. Memory context is selected by simple keyword overlap (up to five records); it is not semantic search and can miss relevant paraphrases. Retrieved memory is contextual data, never tool authorization or an instruction that overrides current user or system safety requirements.

| Method / path | Purpose | Request | Response | Errors / safety |
|---|---|---|---|---|
| `POST /api/memories/extract` | Ask the LLM to identify candidate memories from up to the most recent 50 user-authored messages / 12,000 message characters in one session. This is explicit; conversation messages are not scanned automatically. | `{"session_id": UUID4}` | `list[MemoryRecord]` with `status=pending_approval`, `origin=model_extracted`, and source message reference/excerpt. | `404` unknown conversation; `422` invalid UUID; `503` provider unavailable; `500` storage failure. No candidate is approved automatically. |
| `POST /api/memories/proposals` | Add a user-provided candidate or explicitly requested memory. | `{"content": string, "category": MemoryCategory, "source_session_id"?: UUID4, "source_message_id"?: UUID4, "explicitly_requested": false}` | `MemoryRecord`. | Default creates a pending candidate. Set `explicitly_requested=true` only when the user directly asked to remember this specific content; then it is approved and confirmed. Recognized credential patterns and invalid/non-user sources are rejected. |
| `GET /api/memories` | Inspect pending candidates and approved memories. | Optional `?status=pending_approval` or `?status=approved`. | `list[MemoryRecord]`. | `500` storage failure. Rejected and deleted content is removed; only a fingerprint tombstone remains. |
| `GET /api/memories/{memory_id}` | Retrieve one pending or approved memory for review. | UUID4 path parameter. | `MemoryRecord`, including confirmation/origin/status and source excerpt when present. | `404` unknown memory; `422` invalid UUID. |
| `POST /api/memories/{memory_id}/approve` | Confirm one pending candidate. | No body. | Updated `MemoryRecord` with `status=approved`, `user_confirmed=true`. | `404` unknown memory; `409` not pending. Approval only saves memory; it does not execute tasks. |
| `POST /api/memories/{memory_id}/reject` | Reject a candidate and suppress re-proposal from old transcript content. | No body. | `{"memory_id": UUID4, "status":"rejected", "decided_at": datetime}`. | `404` unknown memory; `409` not pending. Candidate text is removed. |
| `PATCH /api/memories/{memory_id}` | Correct an approved memory's content or category. | `{"content"?: string, "category"?: MemoryCategory}`; at least one field. | Updated `MemoryRecord`. | `404` unknown memory; `409` duplicate or not approved; `422` invalid request. Content corrections clear old transcript source references that no longer support the edited text. |
| `DELETE /api/memories/{memory_id}` | Delete a pending or approved memory. | UUID4 path parameter. | `204` no content. | `404` unknown memory; `422` invalid UUID. A SHA-256 content fingerprint and, when available, source-message tombstone are retained to stop silent re-creation from old history. An explicit new `remember this` request may restore that specific item. |
| `GET /api/memories/settings` | Read the memory retrieval preference. | None. | `{"retrieval_enabled": boolean}`. | Defaults to enabled. |
| `PATCH /api/memories/settings` | Disable or re-enable memory retrieval in conversation responses. | `{"retrieval_enabled": boolean}`. | Updated setting. | Disabling retrieval preserves the memory records and proposal/management APIs; it stops injecting memory into generated conversation context. |

The current API has no authentication or multi-user isolation. Any client able to access the local API can manage all memories. SQLite content is not encrypted at rest; the app-created Unix database file uses restrictive file permissions and SQLite secure-delete behavior where supported, while Windows relies on the local application-data ACL. Messages and extraction prompts go to the configured LLM provider (local Ollama by default when selected, but cloud providers may transmit content off-device). Credential detection is pattern-based and cannot guarantee detection of every secret. The `explicitly_requested` flag represents the direct user request only in this single-user local prototype; do not expose these endpoints beyond a trusted local environment without authentication and authorization.

## Local reminders

| Method / path | Purpose | Request | Response | Errors / safety |
|---|---|---|---|---|
| `POST /api/reminders` | Create a reminder proposal. | `{"title": string, "description"?: string, "due_date": "YYYY-MM-DD" or "today" or "tomorrow", "due_time"?: "HH:MM:SS", "timezone": IANA zone, "explicitly_confirmed": false}` | `ReminderRecord`, normally `status=proposed`. | `422` invalid date/time/time zone; proposals are not active until confirmed. Set `explicitly_confirmed=true` only when the user clearly requested creation of this specific reminder. |
| `GET /api/reminders` / `GET /api/reminders/{reminder_id}` | List or retrieve reminders. | UUID4 for one record. | `list[ReminderRecord]` / `ReminderRecord`. | `404` unknown ID; local single-user data. |
| `POST /api/reminders/{reminder_id}/confirm` | Activate one proposal. | No body. | `ReminderRecord` with `status=active`. | `404` unknown ID; `409` if not proposed. |
| `PATCH /api/reminders/{reminder_id}` | Edit reminder content or due information. | Any of `title`, `description`, `due_date`, `due_time`, `timezone`. | Updated `ReminderRecord`. | Invalid or nonexistent local DST times are rejected; ambiguous times are rejected for clarification. |
| `POST /api/reminders/{reminder_id}/complete` | Mark an active reminder complete. | No body. | Record with `status=completed` and `completed_at`. | `409` unless active. |
| `DELETE /api/reminders/{reminder_id}` | Delete a reminder. | UUID4 path. | `204`. | `404` unknown ID. |

Reminder rows and their notification-attempt journal use separate tables in the same configured local SQLite file as conversation and memory data. Date-only reminders are valid; the standalone Windows user-session agent treats them as due at 09:00 in their stored IANA timezone. `today`/`tomorrow` resolve using the request's time zone. Notifications are independent of FastAPI and the browser after explicit Scheduled Task installation. Reminder responses include `notification_status`, `notification_attempts`, `notification_last_attempt_at`, `notification_submitted_at`, and `notification_error_code`. `submitted` means the OS toast API accepted the request; Windows cannot reliably confirm that the user saw it. The agent catches up overdue active reminders one per polling interval; it cannot operate during shutdown, sleep, or while the user is logged out. This is not personal memory or a task and never invokes tools. The local prototype remains unauthenticated and the SQLite file is not encrypted at rest.

Conversation provider calls have a 90-second default Ollama response timeout (configurable with `LLM_TIMEOUT_SECONDS`), a 5-second connection/pool timeout, and one bounded retry for transient connection errors and HTTP 502/503/504 responses. Timeouts, malformed/empty/truncated responses, and deterministic validation errors are not retried. A retry does not persist a message until a complete reply is accepted; request IDs continue to prevent duplicate persisted exchanges.

Errors use a `detail` object with a stable `code` and safe `message`. Invalid request bodies and path UUIDs return `422`; unknown tasks return `404`. Unexpected errors return a generic `500` response without a traceback.

## Backend startup

From the repository root, in PowerShell (the repository's import convention is `backend.app`):

```powershell
python -m uvicorn backend.app.main:app --reload
```

The API base URL is `http://127.0.0.1:8000/api`; interactive Swagger documentation is at `http://127.0.0.1:8000/docs`.

LLM configuration is optional for application startup and required for task creation and generated conversation replies. Supported environment variables are `LLM_PROVIDER`, `LLM_MODEL`, optional `LLM_BASE_URL`, `OPENAI_API_KEY` or `LLM_API_KEY` for cloud providers, and `LLM_TIMEOUT_SECONDS`. Ollama uses `LLM_PROVIDER=ollama` and defaults to `http://localhost:11434/v1`. `UNBOUND_CONVERSATION_DB` optionally sets the local SQLite file path. Credentials are never returned by the API.

Task and approval state currently lives in process memory and is lost when the application restarts. The default runtime has no browser or report tools. It registers verified read-only `document.search`, `context.retrieve`, and `context.relate` tools against the configured local document store. `document.upload` is registered only when `UNBOUND_DOCUMENT_IMPORT_DIR` is configured and requires approval. Document upload is also available as an explicit user-initiated multipart API operation.

Tasks are not durably journaled. Restart does not restore or replay tasks. The in-process recovery helper retains verified completed work but moves ambiguous failed/interrupted steps to `NEEDS_ATTENTION` instead of automatically retrying an external action. No task persistence should be added without a durable execution journal and an explicit at-most-once/reconciliation design. Errors are logged by exception class/diagnostic only; user-visible API errors omit tracebacks and private exception text. This prototype has no request rate limiting.

External actions already started by a registered callable may not be reversible. Cancellation prevents later steps, but cannot guarantee rollback of an in-flight browser or remote operation.

## Documents

| Method / path | Purpose | Request | Response | Errors / approval |
|---|---|---|---|---|
| `POST /api/documents/upload` | Validate, extract, and persist one local document. | `multipart/form-data` field `file`; maximum file size 20 MiB. | `DocumentUploadResponse` (`document_id`, `original_filename`, `file_type`, `extraction_status`, `page_count`, `chunk_count`, `error`). | `413` too large; `415` unsupported extension; `422` empty/corrupt/failed extraction; `503` storage failure. On Windows the default document store is `%LOCALAPPDATA%\UNBOUND\documents`; set `UNBOUND_DOCUMENT_STORAGE` to choose another local directory. It contains `documents.db`, `files/`, and `texts/`, separate from conversations, memories, reminders, and task state. The default FastAPI runtime registers `document.search`, `context.retrieve`, and `context.relate` with per-tool verifiers. It registers approval-gated `document.upload` only when `UNBOUND_DOCUMENT_IMPORT_DIR` is configured; this tool accepts only a relative path inside that directory. Public upload remains bytes-only.

The standalone MCP server is explicitly launched over stdio and exposes read-only document/context/evidence tools. It does not accept filesystem paths or expose upload because it has no approval manager. No MCP client is implemented, no remote MCP servers are auto-connected, and MCP output/document text is untrusted data. Internal orchestration adapters call the shared document services through the existing ToolRegistry. No `/api/integrations` endpoint is currently implemented.
